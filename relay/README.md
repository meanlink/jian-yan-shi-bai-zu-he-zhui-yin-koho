# 归档简报投递与接收对账（relay 子系统）

质量组把**已归档简报**交给外部接收系统时，网络超时无法区分「对方未收到」还是「已接收但回执丢失」。
本子系统提供一个**零第三方依赖**（Python 标准库 + SQLite）的本地可演示实现：独立接收端、
发送端投递对账台、双方指纹核对、可重放的故障演示与单元测试。

## 运行

```bash
# 端到端演示：9 个场景、全部带断言，跑完保留服务可点页面
python3 -m relay.demo
# CI/验收：跑完即退出并返回退出码
python3 -m relay.demo --once --clean
# 仅启动两个服务（含后台自动调度）
python3 -m relay.run --clean
# 单元测试
python3 -m unittest relay.tests.test_stores -v
```

| 入口 | 地址 |
|---|---|
| 发送对账台 | http://127.0.0.1:8088/app |
| 接收端控制台 | http://127.0.0.1:8089/ui |

运行期数据库写入 `var/relay*/`，已在 `.gitignore` 忽略；`--clean` 会清空重来。

## 状态模型（按归档与目的地跟踪）

| 状态 | 含义 |
|---|---|
| `PENDING` 待发 | 计划生成、尚未被调度认领 |
| `IN_FLIGHT` 待确认 | 已发送，等待接收事实/回执；超时与故障期间停留于此 |
| `RECEIVED` 已接收 | 接收端事实存在且双方 SHA256 指纹一致 |
| `CONFLICT` 冲突隔离 | 同一投递内容指纹不符，终态，不再自动重试 |

状态机**单调推进**（rank 只增不减），转移由单条条件 `UPDATE ... WHERE status=? AND attempt_count=?`
原子完成；任何向回改的动作（晚到回执、并发线程）都会被拒绝并写 `rollback_blocked` 尝试记录。

## 需求点与实现对照

1. **超时先查接收事实，不靠猜**
   发送出现网络异常/5xx 时，`Dispatcher._reconcile_after_timeout` 先 `GET /api/facts/{id}`：
   有事实→按事实补齐；无事实→才安排退避重试；查询本身失败→保持待确认继续退避。
2. **重试不重复接收**
   接收端以 `delivery_id` 为唯一幂等键（`receiver_store.facts` 主键），重复提交只累加
   `duplicate_count` 并再次签发回执，绝不产生第二条事实。
3. **同一投递内容不符→隔离报错**
   接收端对同 ID 不同指纹返回 409 且保留首次原件；发送端将记录置 `CONFLICT`，
   保存双方指纹与差异说明，页面可并排比对内容。冲突是终态，自动调度不再认领。
4. **发送中断恢复，接收成功而本地未记账也能补齐**
   故障开关 `crash_after_accept` 让发送端在对端确认后、本地记账前中断（记录停留 IN_FLIGHT）；
   重启时 `recover_on_startup` 扫描全部在途记录查询事实，指纹一致即补齐 RECEIVED。
5. **并发重试与晚到回执不回退状态**
   认领用 `claimed_at` + 条件 UPDATE 保证多线程只有一个赢家；晚到回执指纹不符直接 409
   且状态不变，指纹正确则幂等保持 RECEIVED；CONFLICT 记录拒绝任何回执翻转。
6. **暂停停止新投递，在途仍可对账**
   `plans.paused=1` 时 `enqueue_for_plan` 拒绝生成新投递；已 IN_FLIGHT 的记录继续被
   调度/对账处理。
7. **改目的地不挪走在途记录**
   投递表 `dest_code` 是创建时的快照；改计划目的地只影响之后新生成的投递。
8. **页面可查双方指纹、尝试记录及差异**
   发送台 `/app`：状态计数、归档版本、计划操作、投递详情（本地/接收端指纹、逐条 attempt、
   字段级 diff、双方原件）、审计轨迹、故障开关；接收台 `/ui`：事实库、重复计数、原件。
9. **旧归档保留原件**
   同标题再次写入生成新版本行，旧行 `superseded_by` 指向新版但内容与指纹不变；
   历史投递永远引用创建时的归档版本与指纹。

## 演示场景（`relay/demo.py`）

1. 正常投递 + 接收端幂等（重复提交不二次落库）
2. 回执回程丢失（事实已在）→ 查事实补齐，不重发
3. 报文丢失且对端无事实 → 查询确认后安全重试，仅接收一次
4. 事实接口同时故障 → 保持待确认退避，恢复后对账补齐
5. 接收端内容改写 → 指纹冲突隔离，终态不被晚到回执回退
6. 发送端记账前崩溃 → 重启恢复扫描补齐
7. 4 线程并发调度仅一个认领成功；错误/正确晚到回执的拒绝与幂等
8. 计划暂停拦新投递、在途仍可对账；改目的地后在途快照不变、新投递走新目的地
9. 归档新版本另存，旧版原件与指纹保留

## 故障注入开关

| 开关 | 位置 | 效果 |
|---|---|---|
| `drop_receive` | 接收端 | 丢弃投递报文（503），发送端超时后查事实 |
| `lose_receipt` | 接收端 | 事实已落库但回执回程 500，模拟「收到但回执丢了」 |
| `drop_facts` | 接收端 | 事实查询接口 503，演示退避保持待确认 |
| `mutate_payload` | 接收端 | 落库前改写内容，制造双方指纹冲突 |
| `crash_after_accept` | 发送端 | 对端接收成功后本地不记账，模拟进程中断 |

## 目录

```
relay/
  fingerprint.py       双方统一的规范化 JSON + SHA256 指纹
  receiver_store.py    接收端事实库（幂等、冲突不覆盖、回执、故障开关）
  receiver_service.py  接收端 HTTP 服务（/api/receive、/api/facts、/ui）
  sender_store.py      归档/计划/投递状态机、尝试与审计（单调、条件更新）
  dispatcher.py        超时查事实、退避重试、恢复扫描、晚到回执
  sender_service.py    发送端 HTTP API + 后台调度线程
  sender_ui.py         发送对账台页面
  receiver_ui.py       接收端控制台页面
  run.py               常驻服务入口与演示数据 seed
  demo.py              9 场景端到端可重放演示
  tests/test_stores.py 状态机/幂等/冲突/并发/归档单元测试
```

说明：本目录刻意只使用标准库，与主工程的 FastAPI/MySQL/Redis 栈解耦，
便于在无 Docker 的环境直接演示；两侧指纹算法与主工程 `utils/serialization.checksum`
口径一致（`sort_keys` + `ensure_ascii=False` + 紧凑分隔 + SHA256）。
